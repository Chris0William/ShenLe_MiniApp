## 先看结论

当前系统适合继续采用 .NET 8 模块化单体 + MySQL + uni-app 小程序。暂不需要微服务、换数据库、换前端框架或直接扩容。优先减少重复工作、收敛数据权限、治理日志，再整理界面和大型页面。

建议顺序：**日志与数据边界 → 媒体索引 → 楼盘查询和地图轻量接口 → 前端请求与刷新 → 页面拆分和视觉统一 → 后台上传及数据版本保护**。

## 这次确认了什么

| 事实 | 意义 |
|---|---|
| 生产有效楼盘 970、楼栋 875、房源 19,005 | 暂无证据需要分库分表；先优化现有查询 |
| `SysLogOp` 数据及索引约 7,735.52 MiB | 日志体积远大于核心盘源数据 |
| 生产 Docker 日志约 5.16 GB，测试约 0.68 GB | 需同时治理数据库日志与容器日志 |
| 生产和测试 `CacheType=Memory` | Redis 在运行，不代表应用缓存已经用上 Redis |
| 封面代表查询 `EXPLAIN` 为 `ALL`，估算扫描 23,412 行 | `SysFile(BelongId, FileType)` 是明确的候选索引 |
| 地图每页 200 条循环拉完整楼盘结果 | 一次地图加载重复触发列表查询与聚合 |
| 楼盘接口先取全量候选，再内存排序分页 | 即使只看第一页也承担候选集计算 |
| 页面返回后有逐页重拉已加载内容的逻辑 | 长列表编辑回来的等待会随浏览页数增加 |

以上是有限时点取样，不是生产压测。服务器当时 CPU 较空闲、可用内存约 5.2 GiB、磁盘尚余约 39 GiB；不能用单次快照推断峰值。

## 不改变的业务约束

1. 没有额外普通用户端；游客使用业务员端外壳做脱敏预览。
2. 房东只能进入房东端；当前该限制主要在小程序，服务端读范围需要专项收敛。
3. 管理顺序继续为楼盘 → 楼栋 → 房源。
4. 地图和列表共享筛选语义。租金 0–10000 双滑块、选点、房号后缀和户型等已确认规则保留。
5. 不恢复地图气泡合并，不额外增加第二个地图，不接外部逆地理编码服务。
6. 图片/视频是一份媒体项，封面为附属文件；不重新启用数据万象。
7. 佣金继续数值输入 0–1000%；宠物文案、颜色和位置沿用已确认规则。
8. 后台上传仅作为后续独立阶段，当前不改变“上传完成后保存”。
9. 旧小程序仅作为历史参考，不跟随本轮重构。
