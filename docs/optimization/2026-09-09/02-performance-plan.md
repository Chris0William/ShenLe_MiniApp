# 02 性能、数据边界与可靠性优化

状态：设计方案。所有指标为验收目标或候选值，未宣称已达到。实施按 [04阶段计划](04-delivery-and-validation.md) 批准后进行。

## 1. 目标和原则

1. 先减少请求次数、扫描行数、序列化体积和重复渲染，再考虑基础设施扩容。
2. 不通过改变筛选含义、减少权限校验、丢弃业务日志、隐藏结果获得“性能提升”。
3. 保留模块化单体；数据库查询优化与页面数据编排逐步迁移，旧接口保持可用。
4. 公共预览、业务员可租数据、房东所属数据、维护人受托数据、管理员数据必须采用不同权限范围，缓存按范围隔离。
5. 生产只做批准的灰度与观测，压测和写入验证在 `adminet_test`，媒体测试使用独立空间。

## 2. P0：先建立安全的观测和日志控制

### 2.1 三种日志分开

| 类型 | 保存内容 | 建议策略 |
|---|---|---|
| 请求技术日志 | 时间、路由模板、方法、HTTP及业务码、耗时、TraceId、返回字节数、SQL计数 | 成功读取采样；异常和慢请求保留；建议7–14天 |
| 错误日志 | 异常类型、脱敏栈、关联TraceId、环境 | 建议30天；敏感输入不入库 |
| 业务审计 | 谁、何时、对哪个对象执行什么动作、结果、批次、字段差异 | 独立于技术日志，保留期限需业务批准 |

当前的完整请求/返回监控会记录大列表、二维码Base64及认证头。优先通过权威 Logging 配置及业务扩展点关闭成功读接口的全量响应记录，验证 `Logging:Monitor` 配置实际被加载。不要直接改 Core 来删除日志能力。

必须脱敏或完全排除：Authorization、Cookie、Token、登录Ticket、手机号授权Code、签名URL参数、二维码图片Base64和证明材料内容。生产排查输出只返回必要字段或统计，不把原始认证头写入方案/台账。

固定入驻码只需要记录生成结果和耗时，不记录图片内容。

### 2.2 历史日志治理顺序

1. 先限制新增量，观察24小时增长，技术日志体积目标较基线降低80%以上，且错误定位能力不退化。
2. 统计时间分布、保留范围和现有索引，提出具体历史删除清单供批准。
3. 对批准删除的数据小批次按主键/时间范围处理，监控锁等待、复制/binlog、IO和线上延迟。
4. 删除数据不保证立即释放物理磁盘。`OPTIMIZE TABLE` 或重建大表需要额外空间和独立维护窗口，不能附带执行。
5. 不备份完整6–8GB日志表；若需保留，只导出批准的必要窗口，压缩后计入存储预算。
6. 业务活动、审批、版本差异不属于可直接删除的技术噪音。

Docker日志建议评估 `max-size=50m`、`max-file=3`，按每容器约150MB预算起步；这是候选配置，不是当前值。必须从本地权威Compose配置发布。日志选项往往需要重建容器，仅 `restart` 不保证生效；重建前检查挂载、网络、镜像和回滚命令。Nginx/file logger 也要各自轮转。

### 2.3 性能观测

- 请求层新增/复用 TraceId，记录 route、业务code、总耗时、SQL次数、SQL总耗时、响应大小。
- 数据库先使用现有 performance_schema 做时间窗差分。仅在批准后临时开启有体积上限的慢日志，候选阈值200–500ms，不能直接长期记录全部SQL参数。
- 报表区分首屏冷缓存、热缓存、业务端/房东端/管理端、页数和筛选条件。
- 定位、网络、API、Vue状态更新、地图marker应用分别计时。一个“总加载时间”无法定位问题。
- 样本中 HTTP 200 可能是业务错误，成功率必须检查业务code。

## 3. P0：在缓存优化前收敛数据范围

当前小程序限制房东只能进房东端，但后端通用楼盘/房源读取主要校验 ViewRealData，而没有把所有通用读取限制为房东所属楼盘。禁止用“客户端隐藏按钮”替代服务端权限边界。

建议在现有 `SlAuthorizationService` 上补统一读取范围解析，避免另建一套角色系统：

```text
认证身份 -> 可进入端 -> 操作能力 -> 查询数据范围 -> 业务过滤 -> 排序分页
```

- 游客：仅公共脱敏DTO。
- 业务员：可租范围，只读真实数据。
- 房东：自己的 `SlLandlordCommunity` 关联范围；即使伪造请求端参数也不能扩大。
- 维护人：管理写入限定受托范围；是否仍可在业务员端看全平台可租数据沿用当前规则。
- 管理员/超管：按已确认能力；删除规则和创建者规则单独保留。
- 账号既是房东又是管理员/维护人的处理须测试真实存量情况并确认。客户端已按房东优先；服务端不能继续无条件叠加后又宣称仅房东范围。

将范围下推到 Page/List/Stats/Detail/媒体解析/导出/批量接口。详情必须根据目标真实所属楼盘授权，不能信任客户端传入的 communityId。

公共预览无区域中心时，不再使用单楼盘坐标均值；方案建议回溯已配置的行政区域中心或显示无点位区域卡片，并给管理端补齐中心点的待办。必须保留“所有区域可展示”的要求，不能以脱敏为由又隐藏小区域。

## 4. P1：候选索引和SQL优化

### 4.1 媒体关系索引：第一优先候选

实际生产代表查询：

```sql
SELECT BelongId, Id, Url
FROM SysFile
WHERE BelongId IN (...) AND FileType = 'image:video_poster';
```

本轮 `EXPLAIN` 显示 type=ALL、无possible_keys、估算扫描23,412行。候选索引 `(BelongId, FileType)`，同时有利于按BelongId读取媒体。若真实关联查询带租户条件，以捕获的SQL和分布决定是否调整顺序。

实施步骤：核验现有索引、字段类型/长度 → 测试库加索引 → 对代表SQL EXPLAIN和限量基准 → 测试上传/封面挂载/复制/删除 → 独立批准后生产加索引。索引不放Url等宽字段，不盲目制造覆盖索引。通过业务迁移脚本管理，避免改Core实体。

验收：代表查询不再全表扫描，扫描行数接近目标视频附属文件数；写入延迟无明显回退，索引名称与回滚DDL留档。

### 4.2 房源过滤索引：按场景选，不全部添加

| 场景 | 候选索引 | 注意 |
|---|---|---|
| 楼盘下可租统计/租金 | `(CommunityId, IsDelete, Status, RentPrice)` | 先测试已有单列索引合并与候选索引收益 |
| 楼栋房态/楼层筛选 | `(BuildingId, IsDelete, Floor)` | 状态和排序字段根据实际SQL调整 |
| 活动榜按时间/操作人 | `(OperatorUserId, OccurredTime)` 或 `(OccurredTime, OperatorUserId)` | 按过滤选择性选一个，避免重复冗余 |
| 更新摘要排序 | `(LastUpdateTime, CommunityId)` | 需与楼盘筛选联表计划共同验证 |

当前房号后缀匹配是 `EndsWith`，通常生成 `%suffix`，普通RoomNo前缀索引不能解决。先利用 BuildingId 限定小范围；只有大量房源下证实仍慢时，再评估反转列/专门房号键。不可把后缀匹配改成包含/前缀匹配。

统计、详情和列表必须复用可租/租金/户型过滤表达式，否则“卡片数量”和“点进去列表数量”仍会不一致。

### 4.3 楼盘分页分场景优化

当前每次请求：全候选轻量行 → 内存距离/排序/切页 → 当页详情 → 房源统计/户型/佣金/联系人/封面。

推荐两个分支：

1. **无需距离排序/距离筛选**：数据库 COUNT + 稳定 ORDER BY + LIMIT/OFFSET；当前显示页才做补充聚合。排序保留更新时间、OrderNo、Id的确定性。
2. **需要距离**：先经坐标边界粗筛，再使用与当前一致的距离计算和精确过滤。注意GCJ-02坐标口径、距离四舍五入边界、无坐标排序、零租金含义。SQL执行可使用参数化表达式，不能为避开SqlSugar问题拼接用户输入。

业务规则先提取为可测查询组件，旧Page与新地图接口共同调用；禁止整套筛选重写后忽略原有特殊条件。

佣金解析可逐步改为 LeftJoin 房源配置及楼盘默认值，在数据库对 COALESCE 后的有效佣金做 Min/Max；保持未填、0%、继承和已下架数据的现有语义。暂不加统计表，先比较SQL聚合收益。

## 5. P1：地图和列表分开取数，共享筛选语义

### 5.1 建议增加轻量地图接口

建议路由：`GET /api/slCommunity/mapPoints`，名称待实施时统一。旧 `/page` 保留。

只返回绘点与选择必需字段：楼盘Id、名称、经纬度、可租数量/状态、数据版本。封面、佣金范围、联系人等完整摘要在选择楼盘后加载，或由轻量摘要接口按一组Id批量获取。

当前约970个有效楼盘，优先测一次返回全量轻点数据的实际体积；目标 <=200KB 未压缩JSON，超过预算再采用分页轻点或视野请求。不能默认只显示附近，也不能悄悄恢复气泡聚合。未登录区域预览继续展示所有可展示区域，接口与真实点位分开。

首屏策略：加载当前角色及必要区域配置 → 并行取轻点/缓存定位 → 地图可用 → 点击点加载详情；榜单、弹幕、联系人候选不阻塞地图可交互。

拖动地图只更新本地显示状态，已缓存全量轻点时不重新查后台。若以后改为视野查询，使用稳定的bbox键、节流、请求版本号，避免边拖边重取和旧结果覆盖。

### 5.2 列表

- 列表保持标准分页，首次只取首页，封面仅加载可见及邻近项目。
- 列表数据与查询键绑定，查询键包含角色端、权限版本、筛选、排序、位置和分享上下文。
- 快速切换筛选时取消或忽略旧请求；不要将“接口返回较晚”误当最终用户意图。
- 列表条目使用稳定Id，不能以索引作为业务实体身份。

## 6. P1：缓存及失效

### 6.1 暂时不全局切Redis

现在单实例Memory并非错误，15分钟授权快照+请求内复用已减少鉴权查询。全局切Redis会同时影响登录票据、分享票据、缓存序列化和锁语义，需要单独测试，不宜作为第一刀。

| 数据 | 建议缓存 | 失效规则 |
|---|---|---|
| 用户权限 | 保留请求内缓存；15分钟TTL上限加主动失效 | 角色、手机号、身份、楼盘归属、维护关系变化立即失效相关用户 |
| 区域/标签字典 | 本地按版本缓存；服务端短TTL | 管理保存后广播/版本递增 |
| 公共脱敏聚合 | 共享短TTL，如30–60秒 | 关键业务变更失效；位置距离单独计算避免无限地理键 |
| 地图轻点 | 按数据范围/筛选摘要键短缓存 | 改状态、价格、归属、坐标后失效相关范围 |
| 详情 | 以实体版本为键，短TTL | 保存后直接回写，删除即剔除 |
| 媒体临时文件 | 有界LRU及路径存在性检查 | 登出/换号清理；失效重新下载；同文件在途请求合并 |

授权失效必须覆盖维护人关系和被影响房东，而不只是操作发起者。遇到分配变更与在途缓存回填，用权限版本/会话代号抵御旧响应。不能只让用户退出重登。

### 6.2 前端共享请求

- 优先扩展已有 `source-contact`、`entity-change`、`location-cache`，不另装一套请求框架。
- `clear()` 增加会话代号，旧Promise完成后比对代号再写状态；跨用户不共用已授权数据。
- 增加按请求键的in-flight去重及适当Abort；不同筛选不能误合并。
- 网络错误与业务拒绝分别处理，失败不缓存成功空数组。
- 保留用户刷新按钮，刷新时强制重新校验该页范围；避免每次onShow无差别刷新。

## 7. P1/P2：编辑后刷新与并发保护

先复用已有实体变更通知，将“重拉全部已浏览页”拆为：

1. 普通字段修改：只取变更实体最新摘要，按Id更新；不动滚动位置。
2. 变更影响筛选命中：删除不符合条目，补齐当前窗口；不要静默展示不匹配结果。
3. 变更影响排序：采用明确策略，保持当前锚点，重新核对邻近页；用户主动刷新时重新排序。是否立即移动到全局新位置需业务确认。
4. 结构性修改/多次遗漏事件：重拉可见窗口并用“首个可见Id+偏移”恢复，而非总从第一页开始。
5. 删除/批量新增后同步统计、地图、房态和选中状态；全选范围仍是用户确认的筛选结果范围。

多人编辑建议增加可选行版本令牌（整数Version或准确到足够精度的专用版本值），更新时 `WHERE Id AND Version`；冲突返回明确的业务结果和最新摘要，不能静默覆盖。

旧客户端兼容：新字段先可选、接口返回先增加，灰度观察旧包；不能立即把未传Version的线上请求全部拒绝。重要字段版本强制时间点需单独定。

## 8. P2：媒体性能与上传状态

### 8.1 保留现有取帧链路

- 首帧是视频附属资源，不把它显示成另一张用户媒体。
- 优先解决文件关系索引、可见图片加载、缓存去重，避免把所有缩略图流量都经应用代理。
- 若进一步用短时签名COS直链，必须先在服务端授权后签发；签名续期、downloadFile域名、跨用户访问和缓存键一起测试。稳定公开对象URL是否符合数据保密目标需审核，不能直接为了速度全部公开。
- 后端代理预览作为兼容回退，保持stream而非读取整文件到内存；按真实文件类型设置响应，检查Range、长度、下载名。通过业务文件服务扩展，不默认改Core。
- 视频上传成功、封面失败时应明确显示“视频成功/封面待补”，支持针对封面重试；不应把已上传视频丢出UI并重复上传原视频。此项需独立契约测试。

### 8.2 后台上传分两步，暂缓实施

**小步版**：仍停留当前表单，显示总体进度、单文件状态、失败重试；上传期间可编辑其他字段，保存必须等必需媒体成功。成功数/失败数可见，不能静默丢文件。

**跨页面版**：需要全局任务队列、草稿所有权、页面退出提醒、临时文件持久化、网络中断恢复、取消和孤儿清理。建议有界并发2条视频起测，每条视频/封面可分别重试；权限变更后暂停并重新授权。不能承诺小程序进入后台/被系统回收后仍持续上传。

用户录屏中的“正在加载”有一段发生在微信选择器内，属于系统取文件/压缩，应用尚未收到tempFiles。增加应用进度条不能消除这段等待。改为原图/原视频会影响大小、流量及50m上传限制，需要真机A/B，而非直接去掉压缩。

## 9. P2：业务模块与大型页面整理

后端保持单体，逐步拆出查询、写入、业务策略、框架适配。优先围绕楼盘查询、权限范围、媒体挂载和活动记录四个边界，不按每张表创建一堆接口。

前端将超过千行页面按明确责任拆：页面数据编排、筛选、地图、选择卡片、媒体预览、表单、批量生成。共用领域逻辑，保留三端独立组合；不要再往全局CSS或所有页面mixin堆业务分支。

分包先看依赖图和真实包体，保证默认路径、5个原生tab壳、旧 `pages/index/index` 和新入驻扫码页仍存在。现有包约1.27MB，体积不是唯一性能指标，不为减包破坏稳定编译依赖。

## 10. P2/P3：重要数据版本与恢复

现有活动日志可回答“谁改了哪个对象”，不能还原字段。推荐选择性记录关键字段差异：价格、状态、费用、佣金、归属、坐标、媒体关系。

- 一条业务命令一个BatchId，记录前值/后值/版本和对象Id，媒体只记文件引用。
- 原子写入业务数据与审计；不能先异步发日志然后在失败时留下“已修改”的假记录。
- 初期保留最近30–90天关键差异，周期快照只用于较大批量变更；容量按真实变更率估算。
- 恢复是新的业务操作，需要权限和当前版本校验，不删除历史、不直接恢复旧数据库文件。
- 成本公式：日变更数 × 平均差异字节 × 保留天数，再加索引；用测试样本测平均字节，不宣称必然“数据爆炸”。
- 删除楼盘级联、批量覆盖等高风险动作优先接入差异与恢复。尚未确认保留时长/恢复权限前不实施。

## 11. 容量与扩容触发条件

完成P1后再评估：持续CPU高于70%、内存可用持续不足1GiB且有swap IO、业务P95超过预算、数据库锁等待持续增长等。需有业务峰值证据。

扩容优先顺序：隔离测试资源/后台批任务 → 单机合理资源上限 → 纵向扩容 → 多实例应用。多实例前必须处理Memory票据/授权缓存一致性、数据库并发锁和任务重复执行。暂不引入微服务、分库分表、Elasticsearch或全量事件溯源。
