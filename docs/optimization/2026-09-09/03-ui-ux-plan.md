# 03 三端界面与体验优化方案

状态：设计方案，不代表这些页面已重做或通过真机验收。

## 1. 设计依据

使用 `ui-ux-pro-max` 做移动业务界面、反馈、信息密度与可访问性检查；使用 `design` 的设计系统路由及 `design-system` 三层Token规范组织样式；通过 `frontend-design` 检查是否偏离实际业务。

本项目是高频房源运营工具，用户要快速筛选、比较、修改和联系。技能检索最初按“real estate”给出了地产营销Hero和展示字体，该结果不适合本项目，**不采用Hero、英文展示字体、滚动入场动画或营销式页面**。后续针对operations、表单和列表检索，仅采纳功能性布局、可见反馈、有界加载等建议。

视觉方向：保留深绿品牌、金色业务强调、白色内容和浅中性背景；提高信息密度，减少大面积渐变、厚阴影、无业务意义的副标题和重复卡片。不是更换品牌，也不重排已经确认的业务流程。

## 2. 三端信息架构

### 2.1 业务员端

保留 `地图 / 房源 / 我的`。

- 地图负责空间选择；房源负责列表比较；两者使用相同筛选定义和业务命中口径。
- 游客显示区域聚合预览，受限功能触发登录/申请，不造一个独立“普通用户端”。
- 已准入业务员展示可租数据、媒体与联系方式。
- 当前业务员端没有“仅看我维护/对接”，本方案不自动开放。
- 房东不能进入业务员端；维护人、管理员继续按已确认规则可切换。

### 2.2 房东端

保留 `地图预览 / 楼盘信息 / 推广 / 我的`。

- 只围绕本人名下楼盘，不提供业务员端/管理端切换。
- 楼盘信息：楼盘列表 → 楼栋 → 房源；费用设置在楼盘层，房源单套覆盖在房源层。
- 推广：同一套房源筛选与选择机制，推广参数与默认佣金清楚分开。
- 我的：昵称、身份、分享二维码、主维护人、电话、退出登录。无多余导航行。
- 退出登录回游客预览，重新登录仍依据最新身份进入房东端。

### 2.3 管理端与维护人

保留 `地图 / 房源 / 工作台 / 销控 / 我的`，维护人使用同一壳但按能力裁剪。

- 地图和房源用于检索管理对象；工作台用于管理入口，不重复堆叠同一批统计/链接。
- 楼盘 → 楼栋 → 房源继续是新增管理主链路，不恢复已删除的跨层“直接发布房源”。
- 超管可以审核用户和房东；管理员的房东分配与超管审批能力必须区分。
- 销控仍是房态批量操作场景，不将状态修改藏到普通详情底部。
- “我的”侧重账户与系统管理，入口采用紧凑分组行，不是每个功能一个大型装饰卡片。

## 3. 页面方案

### 3.1 地图

```text
标题                                  刷新图标
当前位置 / 用户选点                   选点
位置 | 租金 | 类型 | 实时 | 特殊 | 搜索
已选条件：可移除的条件集合
-------------------------------------------
                  单个原生地图
                  独立楼盘气泡
-------------------------------------------
选中楼盘：名称                     可租数量
媒体缩略图    租金范围 / 距离 / 更新时间
水 / 电 / 管理费情况 / 网络费情况
半年、一年佣金                    宠物状态
公告                          查看房源 / 导航
-------------------------------------------
当前端的原有底部导航
```

- 只用一个map实例，保持现有地图首屏修复，不以多个map或cover层替代问题。
- 地图外层固定在可用高度；原生地图内拖动正常，外页面不能被拖出空白。
- 点选卡片高度有上限，长内容在卡片允许区域内滚动或折叠；不遮住关闭、公告和导航。
- 卡片展开先关闭筛选面板；榜单/公告打开时不能残留筛选高亮遮罩。
- 气泡不合并；不因性能优化擅自改变“全部符合筛选楼盘”语义。
- 管理端专用筛选只在管理端出现；超管活动明细和管理员覆盖榜规则继续保留。

### 3.2 楼盘列表

```text
房源 / 楼盘列表                       刷新
位置参考 + 与地图相同的筛选
-------------------------------------------
[封面] 楼盘名称                可租 X 套
       价格范围 / 距离
       费用与包办情况
       佣金                    宠物状态
       更新人 / 对接人 / 更新时间
-------------------------------------------
下一条楼盘
```

- 首行是楼盘名称及数量，第二层是价格/距离，经营信息在固定区域。
- 昵称、楼盘名长文本可换行或显式省略，工具按钮固定宽度不被挤出。
- 摘要组件由地图卡片、列表详情和业务员房源页共享；不同场景选择紧凑/完整密度，不复制字段拼接代码。
- 列表封面只加载可见项；切换图片/视频时保持相同尺寸，避免滚动跳动。
- 点击卡片进入下一层，删除/编辑/导航/保存媒体等操作必须独立阻止事件冒泡。

### 3.3 楼盘 → 楼栋 → 房源管理

```text
返回    楼盘 / 楼栋名称                  刷新
楼层范围 | 房号后缀 | 户型 | 状态
更新人 · 对接人及电话（单行紧凑布局）
-------------------------------------------
多选：全选本筛选结果        已选数量
房源列表 / 销控网格
-------------------------------------------
批量编辑 / 批量删除 / 批量新增（按权限）
```

- 层级标题明确，不能房源列表仍显示楼盘管理而用户不知当前所在层级。
- 所属楼盘/楼栋及总楼层在房源编辑中只读展示；不恢复被删除的单元号输入。
- 更新人不显示电话，对接人电话可以拨号，按已确认位置显示。
- 全选明确采用当前筛选结果，不把“当前页”和“全部命中”混为一谈。筛选变化后重新校验选择集合。
- 超长房号、中文+英文混排、极大数字、空值都有固定布局，不让按钮随内容移动。

### 3.4 批量新增/修改

- 两种生成方式保留：固定房号后缀；每层连续房号。先规则页，点击底部“生成预览”进入预览页，可返回修改。
- 预览只处理当前批次，展示房号、户型、面积、价格、状态和媒体，不加载无关楼盘数据。
- 规则与预览共用同一草稿，回退不丢输入；重新生成前明确覆盖预览调整的行为。
- 批量修改使用每字段“保持/覆盖”的显式意图，空字符串、null和0有不同意义，不能用统一真值判断。
- 大表优先竖向卡行/紧凑行；必须横向表格时只允许表格内部滚动，页面不能跟着横移。
- 底部提交栏显示数量、校验状态；上传中禁止提交，失败项目可见。

### 3.5 我的与申请

```text
[头像] 昵称                         二维码图标
       当前身份 / 修改昵称
-------------------------------------------
管理分组（按权限）
名称                                进入箭头
名称                      待办数     进入箭头
-------------------------------------------
主维护人 / 联系方式（房东）
退出登录
```

- 二维码放头像卡片内部，不单独增加顶栏高度；已有0.4.44已实现此局部调整。
- 入驻码与房源分享码的标题、用途不同，避免只有同形图标而无法区分。多身份场景不同时堆两个无标签码按钮。
- 游客申请业务员仍填写确认过的资料；房东申请不加证明材料；维护人目前由管理端分配。
- 未来统一身份入口需先确认身份定义和审批归属，不自动增加“维护人自助申请”。
- 审核页展示明确状态及时间；禁止提交中的重复点击，审核完成后刷新相关缓存。

### 3.6 Web后台与官网

Web后台更适合复杂批量维护：左侧区域树，中间楼盘/楼栋列表，右侧房源表或抽屉。筛选语义、媒体规则、权限与小程序共用接口；布局可以不同。

官网继续静态展示，不影响小程序主包。仅计划做图片压缩、尺寸占位、缓存和内容一致性检查，未批准前不重新设计官网。线上 `/admin` 与当前 W 分支是否一致需要先比对构建哈希。

## 4. 设计Token建议

采用三层：原始值 → 语义 → 组件。先在新/改造组件使用，逐页迁移旧CSS，不一次替换全局样式。

| 语义 | 候选值 | 用途 |
|---|---|---|
| 品牌主色 | `#126B4F` | 主操作、当前导航、选中 |
| 背景 | `#F5F7F6` | 中性浅背景，弱化大面积渐变 |
| 内容表面 | `#FFFFFF` | 表单、列表、真实卡片 |
| 正文 | `#1E2F27` | 与现有品牌一致 |
| 次级文字 | `#52645B` | 提高当前浅灰说明的可读性 |
| 分隔线 | `#DFE8E1` | 列表分组和边界 |
| 警示/业务金色 | `#946100` | 文本强调，背景用单独浅色Token |
| 危险 | `#C94832` | 删除、错误 |

这些是待视觉验收的值。宠物状态需要遵守“可养金色、不可养黑色加粗、可沟通较浅金色”，保留文字，不只用颜色；针对白色/浅背景实测对比度后确定两种金色，不机械套候选警示色。

- 字体使用系统中文字体，正文14–16px参考值，字段标签14px，标题18–20px，关键价格20–24px；不得按屏幕宽度连续缩放字号。
- 字重400/500/600/700，减少到处800/900；字间距0。
- 间距基准4/8/12/16/24；一般页面左右16px，紧凑行仍保留足够点击区域。
- 内容项圆角4–8px，表单行/页面分区不全部卡片化；模态按现有组件规范。
- 普通按钮高度约44px；纯图标按钮保留至少44px可触控区域、22–24px图标。
- 使用Lucide作为新业务图标目标；优先渐进替换现有Carbon/手写/Wot业务图标，Wot控件内部图标不为统一而大改框架源码。
- 视频媒体固定比例，操作按钮固定尺寸，名称 `min-width:0` 与省略/换行结合。

## 5. 共用组件边界

| 组件/模块 | 承担责任 | 不承担 |
|---|---|---|
| PageShell / Header | 标题、返回、刷新、安全区、单一滚动容器 | 业务鉴权、查询SQL |
| CommunitySummary | 数量、价格、费用、佣金、宠物、联系人和公告摘要 | 自己为每个字段发请求 |
| CommunityFilter / PropertyFilter | 条件编辑、确认、重置、已选展示 | 内部复制角色等级判断 |
| MediaGrid / MediaViewer | 封面、长按菜单、预览、改名、上传状态 | 自己更改业务媒体所属关系 |
| SelectionToolbar | 全选范围、已选数、批量命令 | 自动推断用户想覆盖的字段 |
| OverlayHost | 遮罩、关闭顺序、焦点/触摸归属 | 多层计数器掩盖页面结构问题 |
| QueryState | 首次加载、空态、失败重试、分页 | 默认吞错并当成功空数据 |

## 6. 浮层、滚动与反馈

- 一个页面一个主滚动拥有者。地图固定外层；长列表/表单使用既有兼容滚动模式。
- 模态中需要滚动的内容使用内部scroll-view；原生下拉刷新穿透不能只靠`stopPropagation`修复。
- 优先沿用已经验证的 `disableScroll + 主scroll-view refresher` 模式，打开浮层时关闭背景refresher，等after-leave完成再恢复。
- 不引入重复锁计数器；现有页面原生刷新必须逐页迁移与真机验证，不能全局一刀切。
- 上传、保存和删除的loading归属明确；先结束loading再展示结果，普通结果保留3秒。
- 长流程显示进行到哪一项；失败时给出可读的单条/批次结果，不能一闪而过。
- 动画约160–220ms为候选，关闭过程不提前清空内容；低动效偏好关闭非必要运动。
- 原生video/map和Wot浮层需真机验证；仅设置很大的z-index不算修复。
- 字段错误靠近字段，危险操作确认显示对象和影响范围，不写无意义的“操作成功”充数。

## 7. 加载和性能结合设计

1. 首屏先呈现可用导航和筛选，再渐进显示数据；未知道身份时不可闪现未授权真实数据。
2. 列表占位与最终卡片尺寸一致，避免封面加载导致位移。
3. 地图选中卡片有摘要缓存；更换楼盘先切选中态再请求内容，旧请求不得覆盖新选择。
4. 榜单/弹幕在页面隐藏时停止不必要轮播与请求；再次显示按TTL更新。
5. 图片按可见范围下载；视频仅用户打开时初始化播放器，关闭后释放。
6. 不新增自动播放装饰视频、远程字体、背景大图或沉浸Hero。

## 8. 视觉与交互验收

- 小程序真机：iPhone刘海/灵动岛、安卓不同安全区；至少覆盖320/375/414逻辑宽度及长昵称、长视频名。
- H5/Web：375/768/1024/1440宽度，无横向页面溢出，抽屉/表格内部可独立滚动。
- 所有端图标齐全且统一尺寸，二维码可点击不误触头像。
- 地图只有一个实例、外层不滚、卡片与底部导航不遮挡。
- 弹窗关闭不闪白、无刷新穿透、连续打开关闭不残留遮罩。
- 返回列表保留锚点；编辑后值、筛选数量、可租数量和地图卡片一致。
- 真机验证多视频选择数量、上传逐条结果、保存相册、权限拒绝及重试。
- 不以Playwright/H5截图替代微信原生权限/媒体/map验收。本轮只给结构方案，尚未制作新的UI运行原型或全尺寸截图。
