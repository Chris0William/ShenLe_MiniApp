## 5. 键盘遮挡输入框（全局）
- 现象：textarea/input 获焦键盘弹出时页面高度不变，输入区被挡（公告编辑 remark 最明显，其他页面同病）
- 小程序标准解法（待 5.3 设计选型）：
  1. `adjust-position="{{true}}"`（默认行为，但弹层容器内会失效）
  2. 弹层内输入框用 `cursor-spacing` 撑出键盘上方距离
  3. textarea 获焦时把弹层内容区 padding-bottom 抬升（监听 focus/blur）
- 全局排查点：公告编辑、费用设置 remark、房源表单备注、批量编辑、昵称弹窗

## 6. 筛选条件筛不出数据（bug + 全条件测试）【已有 SQL 证据】
- **测试库实测**：`sl_property` 共 3400 条有效数据，`DepositRule` 有值的仅 **8 条**（1-1×1、2-1×7），其余 3392 条全 NULL；RentalType 仅 `whole`；Decoration 仅 `fine`；Orientation 仅 `east`
- "押一付一筛不出"的直接原因：**存量数据本身没有押一付一**（仅 1 条 1-1 且是北三巷一号 208，状态 0=空置，理论应能筛出该楼盘）
- 待做：
  1. 复测"押一付一"是否能命中北三巷一号这 1 条（后端 Contains 值 `'1-1'` 与前端枚举 `'1-1'` 一致性确认）
  2. **逐条件等价测试**：租金/朝向/装修/租赁/押付/户型（预设组合）/面积/更新时间——每个条件在 adminet_test 用 SQL 对照 API 返回
  3. 顺带确认：这些筛选项在**录入端**（房东设置/批量编辑/房源编辑）是否暴露充分——用户反馈"没见到哪里可设置可短租/可日租"，指向 RentalType 枚举只有 whole/shared/sublease，缺少短租/日租维度（specialModes 的 shortRent/dailyRent 是"可"标记非租赁类型）。需要设计确认：短租/日租是房源级开关还是楼盘级 specialMode
- 录入侧补充需求：**房源级"可短租/可日租"开关**（客户提的）——目前只有楼盘级 specialModes；需设计房源级 `supportsShortRent/supportsDailyRent` 或复用标签体系

## 7. 地图弹幕点击失效（bug）
- 现象：业务员端地图 ①顶部火热招租 ticker ②底部最近更新 ticker ③火热列表弹层里的楼盘行，点击都无法打开对应楼盘卡片
- 回归线索：可能被 P1 动效改动（ticker 结构未动 tap 事件，但需排查 `@tap.stop` 与 focusHotCommunity 链路）；也可能与筛选面板 mask 层级修复（问题 1）相关——修复时统一回归
- 预期行为：点 ticker/列表行 → 地图选中该楼盘并弹出卡片

## 8. 业务员端/房东端地图组件统一 + 佣金排序 + 房源标签
- **8a 组件统一**：业务员端选中楼盘卡片（图3）与房东端"我的楼盘"地图卡片（图4）差异大，以房东端样式为准统一组件；游客可见内容受三开关/佣金隐藏影响（游客不显示租金按开关显示 ???、不显示佣金、公告按开关），业务员全量显示
- **8b 佣金排序**：业务员端"房源"label 楼盘列表（图5）每卡显示佣金条件（半年/一年百分比），并**按佣金高低排序**（越高的越前）。后端列表输出佣金聚合字段已有（lowestHalfYear 等），排序规则需定义（按最高一年佣金降序？）
- **8c 房源标签**：房东端楼栋→房源列表（图6）与业务员端楼盘→房源列表（图7）的房源卡显示标签（押一付一、可日租、可短租等）。现状房源卡只有 `1室0厅1卫 / 0㎡ / 2/2层`，无标签
- **录入缺口**：用户指出"没见到哪里设置可短租/可日租"——见第 6 条，需补房源级开关的录入入口（房源编辑表单 + 批量编辑）

## 9. 地图筛选穿透到房源（大需求）
- 现状：地图筛选只筛楼盘（如押一付一筛出某楼盘，显示 6 套可租，但其中只有 1 套是押一付一）
- 需求：筛选条件**下推到房源级**——楼盘卡片/列表显示"符合筛选条件的房源数"（1 套而非 6 套），点进去的房源列表也只显示符合的房源，并带标签标识
- 技术关联：与 #2 的 layoutCombinations、#8c 房源标签同源——都是"筛选状态贯通楼盘→房源"链路
- 设计要点：楼盘卡片的 availableCount 按当前筛选条件重算；房源列表页接收同一筛选上下文
